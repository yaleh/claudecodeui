# Voice Draft 实验结果：S1（文本阶段消歧）与 S2（长口述 → 增量草稿）

按 `PREREG.md`（提交 `1b710966`，取数之前）判定。只用 `qwen3.8-omni-flash`（听）与 `qwen3.8-flash`（文本阶段，`enable_thinking:false`）。音频全部是 TTS 合成。命令与产物：`s1/an.mts`、`s1/semantic.mts`、`s2/an.mts`；原始读数 `s1/results.jsonl`、`s2/asr.jsonl`、`s2/drafts.jsonl`；S2 人读审计 `s2/audit/`。

## 一句话

- **S1：架构成立。** 让 omni 无上下文地听、再由文本阶段带上下文只输出一张替换表、由本地四条机械校验把关（臂 D），在 A2 里被证伪的上下文方案上变成净收益、零竞争者替换、零编造。唯一没过的预注册条目是「输出可解析率」，原因是两条很长的上下文把文本模型带偏，且失败时不改任何内容。
- **S2：增量草稿这一版没有通过。** 撤回、数字覆盖、语音命令「删掉刚才那段」、搁置的想法都做对了（人读泄漏 0），延迟和成本也很低；但在本轮的提示词下，增量草稿比「全部段一次整理」更容易丢要求，尤其是说话人用「先不用，保持原样」这类**否定性决定**表态的地方（人读召回 0/5，一次整理 80%）。

## S1：文本阶段消歧

输入是 A2 的 13 条片段 × 5 次 omni 无上下文输出（基线 A，rep 0–4，✅ 83.1%），文本阶段对每条输出 × 8 条冻结上下文各跑一次，共 1105 次调用。

| 臂 | 做法 | 改动的输出 | 规则判定 ✅ 增 / 减 / 新 ❌ | 人读判定 ✅ 增 / 减 / 新 ❌ |
|---|---|---|---|---|
| B | omni 带上下文（A2 已有数据） | — | 期望净收益旧 8 条 −16.9pp | — |
| C0 | 文本阶段无上下文（对照） | — | ✅ 84.6% vs A 83.1%（+1.5pp，不伤） | — |
| C | 带上下文，自由改写整理稿 | 59 / 520 | +26 / −6 / 0 | +22 / −7 / **8** |
| D | 带上下文，只输出替换表 + 四条机械校验 | 27 / 520 | +16 / 0 / 0 | **+16 / 0 / 1** |

D 的预注册判定：

| 规则 | 读数 | 结论 |
|---|---|---|
| 1 期望净收益为正（旧 8 条 / 扩展 5 条） | +4.7pp / +2.1pp | 通过 |
| 2 竞争者上线 ≤ A + 5pp | 目标加竞争者 15.6% vs A 15.6%；只含竞争者 2.0% vs 0% | 通过 |
| 3 编造细节 ≤ 2% | 1/520 = 0.2% | 通过 |
| 4 目标加竞争者分层 ≥ A − 5pp | 72.0% vs 50.0%（+22pp） | 通过 |
| 5 无标识符片段 ≥ A − 5pp | 100% vs 100% | 通过 |
| 6 完整性：200 ≥ 95%、可解析 ≥ 95% | 200：100%；可解析 83.5% | **不通过** |
| 7 文本阶段延迟只报告 | p50 1.7 s，p90 6.2 s | — |

- 规则 6 的失败**全部来自 c4、c7 两条上下文**：去掉它们后可解析率是 98.5%（D）/ 99.7%（C）。c7 让模型返回纯文本而不是 JSON；c4（8k 字的助手长回复）让模型把上下文当成要续写的内容，事后的探针（不入数据）里，C 的返回长达 3692 token，开头是上下文里助手回复的「我先并行做两件事…」。解析失败时 D 与 C 都退回原整理稿，所以没有伤害，但这是预注册的条目，按规则它是未通过。
- 这也说明文本阶段**同样会被长上下文带偏**。C 的自由改写把这种带偏变成了输出（人读 8 处新 ❌：续写成助手回复、凭空换成另一个文件、把口头禅放回去、把被禁改的文件写成要改的文件）；D 的替换表结构上无法承载这类内容，所以几乎没有伤害。
- D 的收益集中在拼写：`voice.rounts.ts → voice.routes.ts`、`chatcomposer.tsx → ChatComposer.tsx`、`voice.se → voice.service.ts`（d04 的禁改文件）、`block → blob`。27 处改动里人读认为错的有 2 处（`voice.ts → voice.routes.ts` 把目标换成了另一个真实文件；`voice.rounts.ts → voiceTrim.ts`），另有 2 处无意义的半截替换。
- D 拒绝了 31 条替换：12 条因 `from` 本身已是合法名字（正是 A2 里 d01 被换成 routes 的那类），11 条因编辑距离过远，8 条因 `to` 不在上下文或仓库里。
- 整体 ✅ 约从 83.1% 升到 86.2%（+3.1pp，由 +16/520 折算）；剩下的错误大多是听音就没有信息的（`voice.se.res.ts` 里没有 service 的音）。
- **S1 结论**：把上下文挪到文本阶段、且只许输出可被机械校验的替换表，是 A2 否决方案的可行替代；自由改写（C）不是。需要处理的是长上下文下的格式失败（截断上下文、或在 D 里加 JSON 模式/重试）。

## S2：长口述 → 增量草稿

5 条脚本（L1–L5，11–13 个发言单元，含撤回、数字覆盖、搁置、语音命令、含「删掉」字样的内容句、指称）× 2 个音色 × 3 次识别；每个（脚本 × 音色 × 次）跑臂 a/b/b0/c，另有脚本原文的 ga/gb 各 15 次，共 150 个 run。

**机械召回系统性偏低。** 人读审计（见下）发现 41 处机械/人读不一致，其中 39 处是机械判「未满足」而人读判「满足」，只有 2 处反向；泄漏 96 次判定里只差 1 处。原因是谓词写得偏严（要求某个具体措辞，如 L3.I4 要求「先查状态」、L2.I8 要求出现「旧标题」）。因此机械召回只能当下界，**判定以人读为准**。

### 读数说明

1. **语音命令、撤回、数字覆盖、搁置的想法基本做对了。** 5 条脚本里每一条「删掉刚才那段」都生效，各臂人读泄漏为 0，唯一的例外是 c 的一个 L2 run：命令和被删的那一段落在同一个批次里，被删的「20 字上限」没有被删掉（评审备注：「删掉刚才那段」没生效）。批处理模式下命令与目标同批时容易失效。数字覆盖 100%（c 86%）。这是文本阶段不带音频、只看文字就能做到的事，且 `delete_segment` 由程序按来源段确定性执行。
2. **增量的短板是「决定不做」。** 说话人问「要不要把这段删掉旧标题的逻辑一起改？先不用，保持原样」时，增量臂 b 在 18 个相关 run 里有 15 个对该单元只输出了 `noop`（L2 5/6、L3 4/6、L5 6/6；另有 1 个输出 `park`、2 个空操作或 `modify`），最终稿里就没有这条约束；一次整理保留 80%。这是**可修的提示词问题**（把明确的「保持原样 / 不用写进 task 文件 / 留着当兜底」定义成要写入的约束），不是增量机制本身的上限，但本轮没修，也就不通过。它同时说明：含「删掉」字样的内容句**没有被误当作命令**——泄漏为 0——这是判定 8 里更要紧的那一半。
3. **标识符：上下文有帮助，但帮不到听错了又不在清单里的名字。** b 67% vs b0 44%，方向与 S1 一致（样本小：12 与 9）。无法修复的识别错误占主导：`dist-client → dist-cli`（产物目录是构建生成的，不在文件清单里）、`vite build --watch` 丢掉了 `--`（口述的「杠杠」在整理稿里消失）、「活动坞 → 活动物」、`useChatComposerState.ts → useChatConPostRest8.ts`（后者在清单里却没被修正，文本阶段对清单是保守的）。
4. **编造很少，且多是识别错名被原样带进草稿。** 非识别类的编造只有零星几处，例如一次整理的草稿里出现了「保留现有的节流逻辑」，增量无上下文的草稿里多出一句「作为当前 dev server 的补充选项」；把 WebSocket 误写为 WebRTC 则是识别错误。
5. **上下文胶囊对增量没有明显的整体收益**（召回 b 80.3% vs b0 83.0%，样本太小），只在标识符上看到方向。
6. **一次整理（a）是强基线。** 在这 5 条脚本的长度下，把全部段一次整理召回最高、成本最低。增量的价值不在召回，而在「边说边看到草稿」的体验、以及可以对单段执行删除/撤销；要证明它值得，需要先把「决定不做」补上，并测更长的口述（本轮最长约 3 分钟）。

| 项 | 读数 |

## 偏差与更正（按发现顺序）

1. **S1 原始文本未保存。** 运行脚本只保存了解析后的 `instruction`，没有保存模型原始返回；事后用一次探针（不入数据）确认了 c4 带偏、c7 返回纯文本。
2. **S1 基线口径。** PREREG 写「同一批片段在 A 的 ✅ 率」；实现取 A2 `none` 臂的 rep 0–4（与文本阶段看到的输入配对）。A 用全部 10 次是 80.0%，用 rep 0–4 是 83.1%。
3. **S2 谓词两处缺陷（取数后发现，修复后重算）。** ① `normalize` 把换行也删了，列表项之间的否定语境会串到下一条（既会少算泄漏，也会误伤召回）；② L2.I9 的动词没覆盖「不要修改」。修复后自检仍通过，机械召回 b 从 71.4% 变为 71.8%，其余变化 ≤ 1.5pp，不改变任何结论。上表的机械数是修复后的版本。
4. **S2 抽样脚本缺陷。** 第一次抽样没有覆盖 L5，不符合 `audit.md`；改为按脚本分层（每脚本 6 份，每臂 7–8 份）后重新抽样，再提交评审。
5. **审计合并出错一次。** 我用 Python 字典展开拼对照表时，原始编号覆盖了打乱后的编号，导致评审结果与草稿对不上；我误以为评审员输出有误，让他们重做了一遍（并要求键与清单严格一致），并删除了第一次的输出文件。第二次评审的结果全部通过键一致性校验。
6. **没有人读审计 ga/gb**，所以判定 7 只有机械读数。
7. **评审员是 Claude 系列模型，与作者同属一个会话中的模型家族**；评审规程和抽样种子在读数前写进 `audit.md`。评审员只看到草稿、说话人的原话和标准答案，不知道臂。

## 局限

- 音频是 TTS 合成，单元边界是理想切法；真实 VAD 会切断词与跨段更正（S3 未测）。
- 每个（脚本 × 音色 × 次）只有一次草稿运行；人读审计每臂 7–8 份，臂间差异里小于约 10pp 的都不应当解读。
- 标准答案与谓词由同一人写成，题材偏向语音与 composer；一次整理（a）和增量（b）用的是同一套规则提示词。
- 增量臂的提示词没有为「保持原样」这类决定写明处理方式，这是本轮失败的主因，不是实验设计之外的随机现象。

## 下一步（供确认，不自动执行）

1. 修增量提示词里的「否定性决定」：明确要求「说话人表示先不改 / 保持原样 / 不用写进某处 / 留着当兜底」时输出 `add`（作为约束），然后**按同一份预注册只重跑 b**（约 30 个 run，约 ¥0.2）。这属于预注册的偏离，需要你确认后才做。
2. S1 的 D 臂加 JSON 模式或重试，并在长上下文（c4）下截断上下文，再测一次完整性。
3. 再做 S3（真实 VAD 切段），因为目前 S2 的好成绩都建立在理想切段上。
